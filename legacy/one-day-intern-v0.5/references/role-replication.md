# 把自己的岗位经验做成试岗包

先选一件你亲历过、能代表岗位日常的难题。候选人在熟悉的飞书里接任务、与模拟同事沟通、提交成果，再回顾自己是否喜欢这种工作方式。AI 反馈用于讨论具体产出；人负责后续的岗位匹配判断。

| 准备什么 | 产品经理样例 | 换成客户成功岗 |
|---|---|---|
| 业务情境与固定事实 | 新手卡在发布设置，五天出 demo | 客户要求明天上线，标准集成还需要五个工作日；可先提供手动导入试用 |
| 协作角色与冲突 | 老板要更多功能，研发报成本，导师提示判断方法 | 客户负责人催上线，交付同事说明限制，导师帮助明确客户真正目标 |
| 候选人要交的成果 | 一份 PRD：目标、指标、范围、风险 | 一份客户回复和协调方案：上线目标、阶段交付、责任人与下一次沟通时间 |
| 判断依据 | 用户问题是否清晰、指标是否相关、范围与风险是否合理 | 是否澄清客户目标、尊重真实交期、给出可行分期、明确行动与风险 |

**复刻步骤：**复制 Skill 目录并修改 name、description 与 UI 名称，使触发语句指向新岗位；替换人物/业务事实、短版材料、任务模板和 rubric。同步直播协议中的角色路由、文档标题及反馈项目；若更换角色键，也需修改状态初始化和测试。运行状态、CLI 身份、回执去重和恢复机制继续复用。当前运行器只运行内置岗位，不会收到一句岗位名称就自动生成新包。

**准备三份真实样例：**明显缺信息的首稿、合理取舍后的修订稿、无理由全盘答应的反例。让新包分别跑一次，检查评价是否跟随实际内容；不要照搬产品经理的“2/5”预跑条件，新的首稿与五项 rubric 必须重新对齐。

**保留来源：**模板、导师提示、候选人本人输入分别记录。一个写得完整的模板不等于候选人已经表现出相应能力。业务材料使用虚构或允许使用的案例；不要把演示称号或分数当作自动录用结论。

复制完成后，先做一局真实飞书试岗，检查候选人能否读懂任务、编辑成果、收到具体反馈。之后再按自己的面试节奏调整讲解与体验时长。
