# 共同署名邀请：邀请与处理流程

状态：PRD P0／原型 D0，待评审工作稿。配套剧本见 [完整剧本](../references/scenario.md)。

这是一份交给实习生接手的有内容工作稿。已知事实、设计建议和待决事项分别标注。开局时必须将下列界面底稿制作成文档内的可编辑画板，并验证链接与编辑权限；不能仅把当前文本示意图交给玩家就声称原型已经就绪。

## 1. 背景与用户问题

青橙现有视频由一个账号上传并展示在其主页。多人共同创作时，其他人需要重复上传才能在自己主页展示，导致评论与互动分散。反馈 F01 描述了这一场景。

共同署名希望让同一作品拥有多位创作者入口，保留同一个作品详情与互动集合。F02 和 F03 表明，受邀者需要先识别邀请人并查看成片；F04 表明，原视频提交不应等待所有人完成处理。

本轮目标：把“发出邀请—受邀人处理—发起人查看结果”说明到设计和研发可据此实施的程度。

## 2. 已知产品约束

以下是故事中固定的当前能力，不是对飞书或真实青橙产品的声明。

- 视频已有唯一作品 ID；从共同作者主页进入时指向同一作品，不另建视频副本。
- 原视频按现有流程由上传者发布；共同署名不是对视频剪辑、删除或账号控制权的转让。
- 本期仅讨论已发布、可访问的公开作品。非公开作品不出现发送共同署名邀请的入口。
- 现有系统能够选择账号、发送站内通知、建立共同作者关联，并展示该作品的主页卡片。
- 界面上“等待处理”“接受”“拒绝”可以分别记录；点两次按钮不能产生两份共同作者关系。
- 受邀者处理邀请时需要重新检查作品和邀请是否仍有效。作品已删除或不可访问时，不能继续建立新关联。
- 转码、审核、推荐排序与视频内容编辑沿用现有机制，不在本需求内重做。

新增能力的成本由 Ethan 据方案确认，未知工期不由玩家或导演随口编造。

## 3. 本轮边界

包含：邀请入口与选择、邀请预览、接受与拒绝、发起人查看处理结果、重复操作与作品不可用时的提示。

暂不包含：收益分账、共同编辑视频、陌生人批量邀请、定时催促、跨平台分发、共同作者解除关系的完整新流程。后续解除关系需求单独记录，不以此阻断本轮对邀请流程的评审；原有平台移除与举报能力仍按既有规则处理。

## 4. 现有草案流程

1. 上传者在已发布作品上点击“邀请共同作者”。
2. 选择参与者并发送。发送成功后看到邀请记录。
3. 受邀者收到通知，进入邀请页，查看作品、邀请人以及操作说明。
4. 受邀者接受或拒绝。两边页面按同一结果更新。
5. 接受时建立共同作者关系；主页展示的具体时点待本轮与运营 O0 核对后确认。

待决 Q1：未接受时，是否仅保留邀请记录，还是已经产生主页展示？D0 倾向本人接受后展示，O0 的对外说明不同。需形成唯一决策。

待决 Q2：拒绝结果对邀请人显示“已拒绝”还是“未加入”等中性文案？两者都需让发起人明确它已不再等待处理。

已定行为：未选择账号时按钮不可提交；发送成功显示“已发送邀请”；已存在待处理或已接受关系的账号不重复创建邀请。发送失败时保留所选账号，显示可重试提示。

待 Q1 决定后核对说明文案，不能一面写“等待处理”，另一面暗示已进入所有人主页。

### P02 · 受邀者：查看与处理

```text
┌────────────────────────────────┐
│ ‹  共同署名邀请                 │
│ 小林邀请你成为共同作者           │
│                                │
│ [视频封面                  ▶]  │
│ 我们的最后一个夏天               │
│ 上传者：小林                    │
│                                │
│ 接受后，你会出现在共同作者列表中 │
│ 主页展示条件：见待确认 Q1         │
│                                │
│ [拒绝]       [接受共同署名]      │
└────────────────────────────────┘
```

已定行为：展示邀请人和可预览作品；拒绝与接受都必须有操作结果；关闭页面不等于拒绝；在请求返回之前避免重复触发；失败时不能显示成功。

已处理邀请再次打开时显示真实最终状态，不再呈现可重复建立关系的按钮。作品不可访问时替换为明确说明，禁用接受操作。

此处的“待确认 Q1”是设计草案注释，评审稿必须替换为用户读得懂的实际后果。

## 6. 规则表 R0

| 编号 | 条件与动作 | 预期结果或本轮待定内容 |
|---|---|---|
| R01 | 上传者对有效公开作品选择账号并发送 | 创建邀请并通知对应账号；保留作品 ID、邀请人和受邀人关系 |
| R02 | 对相同作品、相同受邀者重复发送，原邀请仍待处理 | 不创建重复待处理邀请；回到已有记录，不重复轰炸通知 |
| R03 | 受邀者未处理或关闭邀请页 | 邀请保持待处理；是否产生主页展示由 Q1 决定并在此落文 |
| R04 | 受邀者接受，作品和邀请仍有效 | 建立一次共同作者关系，更新两端状态；主页展示时点与 Q1 一致 |
| R05 | 受邀者拒绝 | 记录拒绝，不能当作接受；双方展示文案及本轮再邀请规则由 Q2 补充 |
| R06 | 同一处理动作重复提交 | 返回已处理结果，不重复建立关联或成功通知 |
| R07 | 邀请处理前原作品删除或变为不可访问 | 显示作品不可用，不建立新关系；发起人看到该邀请已失效 |
| R08 | 请求失败或网络中断 | 保留当前内容并提示重试；最终状态以服务端回查为准 |
| R09 | 接受和拒绝请求并发 | 首个成功处理决定状态；后续请求返回现有结果，两端刷新一致 |

本轮需要玩家把 Q1、Q2 的选择、理由和界面后果写到对应行中，移除待确认标记。团队提供的 R01、R02 等现成内容不计作玩家独立产出。

## 7. 验收用例工作稿

| 用例 | 操作 | 应观察的结果 |
|---|---|---|
| T01 | 给一个新账号发出邀请 | 受邀账号收到与正确作品关联的邀请；上传者看到待处理记录 |
| T02 | 对方打开后关闭，未作选择 | 仍待处理；主页与署名行为符合最终 R03，不默认发生接受 |
| T03 | 接受有效邀请 | 两端显示同一结果；只有一份共同作者关系；详情仍指向原作品 |
| T04 | 拒绝有效邀请 | 填入最终 Q2 的两端结果；明确与“等待处理”的区别 |
| T05 | 连点两次接受或重复回调 | 不出现重复署名、重复关系或重复成功通知 |
| T06 | 一部分接受，另一部分未处理 | 原视频仍可访问，已处理与未处理结果分别显示，不要求全员齐备 |
| T07 | 收到邀请后，原视频被删除，再点击接受 | 显示作品不可用，不建立新关系 |
| T08 | 接受请求失败后重试 | 不提前显示接受成功，重试与回查得到一致最终状态 |

验收前由玩家补全 T04，并为最终 Q1 加一个明确检查主页前后状态的步骤。测试数据是模拟账号与模拟视频，不涉及真实用户作品。

## 8. 如何观察上线后的效果

本轮只评审方案，不声称取得上线数据。后续验证建议记录邀请发送、有效送达、打开、接受、拒绝及处理失败事件；统计时按唯一邀请去重。

可观察“有效送达邀请中有多少被处理”，同时观察重复通知、非本人操作引起的主页展示投诉，以及处理失败情况。这里不预填成功增长比例，不把拒绝率简单当作坏结果。

学校活动是否要求全员署名与产品邀请是否正确处理分开记录，避免拿运营收齐人数作为强迫用户接受的理由。
